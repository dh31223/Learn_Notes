### 三、判断题（每题2分，共16分。正确打✓，错误打✗）

**1.** `nn.Sequential` 可以接受一个 Python list 作为参数，如 `nn.Sequential([nn.Linear(10,5), nn.ReLU()])`。

**2.** 测试集应该使用和训练集一样的数据增强（如 RandomHorizontalFlip），以保证数据分布一致。

**3.** ResNet 的残差连接（skip connection）在反向传播时给梯度提供了一条"高速公路"——恒等映射的导数为 1，即使 F(x) 路径的梯度很小，总梯度也不会消失。

**4.** 在使用 StandardScaler 时，应该先对整个数据集（包括训练集和测试集拼接后）进行 fit_transform，再拆分为训练集和测试集，这样可以保证归一化参数更准确。

**5.** GRU 中的更新门 z_t 接近 0 时，表示当前输入很重要，应该写入新记忆；z_t 接近 1 时，表示当前输入不重要，保留旧记忆。

**6.** 在全连接层后应该使用 `nn.BatchNorm2d`，在卷积层后应该使用 `nn.BatchNorm1d`。

**7.** 数据增强后的训练 loss 通常比无增强时的训练 loss 更高，这是正常现象——增强提高了训练难度，模型在学规律而不是背答案。

**8.** Embedding 层的权重矩阵在训练开始时是随机初始化的，语义相近的词在向量空间中靠近是通过训练过程中的梯度更新学出来的。

#### 代码题 2：找 Bug——同事的训练代码（15分）

**材料：**

同事小明写了以下代码，想训练一个 CIFAR-10 分类模型。他说代码能跑，但训练 10 个 epoch 后测试准确率只有 10%（等于随机猜）。请你帮他找问题。

```python
import torch
import torch.nn as nn
import torch.optim as optim
from torch.utils.data import DataLoader
from torchvision import datasets, transforms

# 数据准备
transform = transforms.Compose([
    transforms.RandomHorizontalFlip(),
    transforms.RandomCrop(32, padding=4),
    transforms.ToTensor(),
])

train_data = datasets.CIFAR10(root='./data', train=True, download=True, transform=transform)
test_data = datasets.CIFAR10(root='./data', train=False, download=True, transform=transform)

train_loader = DataLoader(train_data, batch_size=64, shuffle=True)
test_loader = DataLoader(test_data, batch_size=64, shuffle=False)

# 模型
class MyModel(nn.Module):
    def __init__(self):
        super().__init__()
        self.conv1 = nn.Conv2d(3, 32, 3, padding=1)
        self.bn1 = nn.BatchNorm2d(32)
        self.pool = nn.MaxPool2d(2, 2)
        self.conv2 = nn.Conv2d(32, 64, 3, padding=1)
        self.bn2 = nn.BatchNorm2d(64)
        self.fc1 = nn.Linear(64 * 8 * 8, 256)
        self.bn3 = nn.BatchNorm1d(256)
        self.fc2 = nn.Linear(256, 10)

    def forward(self, x):
        x = self.pool(self.bn1(self.conv1(x)))
        x = self.pool(self.bn2(self.conv2(x)))
        x = x.view(x.size(0), -1)
        x = self.bn3(self.fc1(x))       # 第24行
        x = self.fc2(x)                  # 第25行
        return x

model = MyModel()
criterion = nn.CrossEntropyLoss()
optimizer = optim.SGD(model.parameters(), lr=0.01, momentum=0.9)

# 训练
for epoch in range(10):
    model.train()
    running_loss = 0.0
    for images, labels in train_loader:
        optimizer.zero_grad()
        outputs = model(images)
        loss = criterion(outputs, labels)
        loss.backward()
        optimizer.step()
        running_loss += loss.item()
    print(f'Epoch {epoch+1}, Loss: {running_loss/len(train_loader):.4f}')

# 测试
model.eval()
correct = 0
total = 0
with torch.no_grad():
    for images, labels in test_loader:
        outputs = model(images)
        _, predicted = torch.max(outputs, 1)
        total += labels.size(0)
        correct += (predicted == labels).sum().item()
print(f'Accuracy: {100 * correct / total:.2f}%')
```

## 一、单选题

**1. B**
**解析**：`reshape()` 在内存不连续时会先调用 `contiguous()` 复制数据，再执行 view；`view()` 严格要求张量在内存中连续，否则报错。A 说反了，C 忽略了内存连续性的差异，D 错误——view 共享存储（不创建新空间）。

**2. C**
**解析**：训练 acc 98% 验证 acc 72% 是典型的过拟合。换更大的模型（ResNet-152）只会让过拟合更严重——模型容量更大，更容易背答案。应该优先加正则化手段（增强/Dropout/Label Smoothing）。A、B、D 都是合理的防过拟合方案。

**3. B**
**解析**：train 模式：BN 用当前 batch 的均值和方差做归一化，同时用指数移动平均更新 running_mean/running_var。eval 模式：BN 使用训练阶段累积的 running_mean/running_var，不再更新。如果忘了 model.eval()，推理时会用当前 batch 的统计量，导致结果受 batch 组成影响（小 batch 时尤其明显）。

**4. B**
**解析**：Teacher Forcing 在训练时将真实的上一步数据作为当前步的输入，防止模型在自己的错误预测上越跑越偏。推理时因为没有真实标签，只能用模型自己的预测。A 描述的是推理模式而非 Teacher Forcing，C 说的是推理时有真实数据（错误），D 把 Teacher Forcing 和 Dropout 混淆了。

**5. B**
**解析**：ReLU 的正半轴导数为 1，缓解了梯度消失，但带来了 Dead ReLU 问题（负半轴梯度为 0，神经元可能永久死亡），且并未"彻底解决"梯度消失。A、C、D 均正确。

**6. C**
**解析**：每类 < 10 张属于极少数据场景，应该用迁移学习的特征提取模式——冻结所有预训练层，只训练新分类头。A 会严重过拟合，B 数据太少解冻所有层会破坏预训练权重，D 解冻后三个卷积块依旧有较多参数需要训练，风险高。

**解析**：B pin_memory 加速 CPU→GPU 传输；C persistent_workers 避免每个 epoch 重启子进程的开销；D drop_last 保证 batch 大小一致（对 BN 重要）。A 错误——num_workers 过大导致进程间通信开销超过收益，存在最优值；E 错误——shuffle 在每个 epoch 开始时都会重新打乱。

**3. ABDE**
**解析**：A（小 batch BN 统计量不准，LN 不受 batch size 影响）、B（Transformer 默认 LN）、D（RNN/LSTM 中序列长度变化，BN 在时间维度难以应用）、E（LN 对每个样本独立归一化，不受 batch 内其他样本影响）均适合 LN。C 是大 batch CNN 分类，BN 效果更好。

**4. ABCE**
**解析**：A cuda() 移到 GPU；B to('cuda') 同上；C non_blocking 异步传输到 GPU；E 创建层时直接指定 device。D cpu() 是移到 CPU，反向操作。

**问题 3**（6分）

**参考答案**：

**BN 正则化效果的来源**（2分）：
BN 在每个 batch 上用当前 batch 的均值和方差来近似全局统计量。这个近似天然存在误差（被称为"幽灵误差"），因为当前 batch 的统计量不等于整个数据集的统计量。这种随 batch 变化的归一化行为相当于在训练过程中引入了随机噪声——这种噪声起到了正则化的作用，防止模型对特定 batch 的统计特性过拟合。

**与 Dropout 正则化的本质不同**（2分）：
- **Dropout**：在**前向传播**阶段主动随机丢弃神经元，是显式设计的正则化手段。目标是防止神经元之间的共适应。
- **BN 的正则化**：是**意外的副作用**。BN 最初的设计目标是加速训练（缓解内部协变量偏移、稳定梯度流），正则化效果是因为 batch 统计量的随机性带来的隐式噪声，不是设计意图。

**batch_size 减小到 4 的影响**（2分）：
当 batch_size 从 32 减小到 4 时：
- 当前 batch 的统计量（均值/方差）估计更加不准——4 个样本的统计量波动远大于 32 个样本
- BN 的正则化效果会**增强**（噪声更大）
- 但同时 BN 的加速效果会**削弱**（统计量太不准，归一化后的分布不稳定，甚至拖慢收敛）
- 当 batch_size ≤ 4 时，通常推荐换成 LayerNorm 或 GroupNorm

**评分标准**：
- BN 正则来源解释清楚得 2 分
- 与 Dropout 对比准确得 2 分
- batch_size 影响分析正确得 2 分

**问题 2**（7分）

**参考答案**：

**LSTM 为什么比 RNN 更能处理长序列**（4分）：

核心原因在于**细胞状态 c_t 的更新是加法而非乘法**：
```
c_t = f_t ⊙ c_{t-1} + i_t ⊙ c̃_t
```

- RNN 的隐藏状态更新是 h_t = tanh(W·h_{t-1} + ...)，反向传播时梯度要连乘 W_hh。如果 W_hh 的特征值小于 1，seq_len 次连乘后梯度指数衰减到 0（梯度消失）。
- LSTM 中，c_{t-1} 到 c_t 经过的操作只有逐元素乘法（遗忘门 f_t）和加法（+ i_t ⊙ c̃_t）。如果遗忘门 f_t 接近 1，c_{t-1} 几乎原封不动穿过时间步。反向传播时，∂c_t/∂c_{t-1} 接近 1，梯度不衰减。
- 这个设计和 ResNet 的残差连接是同一个思路——提供一条可以让梯度无衰减通过的"高速公路"。

**f_t 始终接近 1 的含义**（3分）：

如果遗忘门在某个维度上始终接近 1，说明模型认为这个维度存储的信息对当前任务**始终很重要**——比如在情感分类中，这可能存储了"这句话到目前为止的情感倾向"。f_t=1 意味着"这条信息不要忘，一直保留到最后"。这是 LSTM 的长距离记忆能力的体现——信息可以跨越几十上百个时间步不被冲刷。

**评分标准**：
- 加法更新 vs 乘法更新的对比解释清楚得 4 分
- f_t=1 的含义解释正确得 3 分

### 材料 3（15分）

**问题 1**（5分）

**参考答案**：

**根本原因——梯度消失**：

反向传播时，梯度从输出层向输入层逐层传递，每经过一层就要乘以该层激活函数的导数。Sigmoid 的导数最大值为 0.25（在 x=0 处），在饱和区（|x| > 3）导数几乎为 0。

5 层网络中，梯度从第 5 层传到第 1 层，每层最多乘 0.25，连乘后梯度衰减为原来的 (0.25)^5 ≈ 0.001——几乎消失了。所以深层（靠近输出）还能收到更新信号，浅层（靠近输入）几乎收不到。

Sigmoid 在这个场景下尤其不利的原因：
- 导数在所有区域都 ≤ 0.25，没有像 ReLU 那样导数为 1 的区域
- 容易饱和（两端导数为 0）
- 没有 BN 来稳定各层的输入分布，Sigmoid 更容易进入饱和区

**评分标准**：梯度消失机制解释清楚得 3 分，Sigmoid 的不利原因得 2 分。

---

**问题 2**（5分）

**参考答案**：

**梯度爆炸的恶性循环**：

1. 学习率过大（0.5）→ 一次参数更新后，权重被推到一个很大的值
2. 大权重 → 前向传播时激活值很大 → Sigmoid 进入饱和区（导数为 0）或 ReLU 输出极大
3. 大激活值 → 损失函数的值变大 → 反向传播计算出的梯度异常大
4. 大梯度 × 大学习率 → 权重被推到更大的值 → 循环加剧
5. 短短几步后，激活值或参数值超过了 FP32 的表示范围 → inf
6. 损失函数中 inf 参与计算 → NaN

这是一个正反馈循环：大权重 → 大梯度 → 更大的权重 → 更大的梯度 → 爆炸。

**评分标准**：能描述正反馈循环得 3 分，提到数值溢出导致 NaN 得 2 分。

---

**问题 3**（5分）

**参考答案**（至少 4 项，每项约 1.25 分）：

1. **将 Sigmoid 换成 ReLU 或 Leaky ReLU**：ReLU 在正半轴导数为 1，不会像 Sigmoid 那样连乘衰减。这是最关键的修改。

2. **添加 BatchNorm 层**：在每层卷积/全连接后、激活函数前加 BN，稳定各层输入分布，防止 Sigmoid 进入饱和区。

3. **使用合适的权重初始化**：
   - Sigmoid/Tanh → Xavier 初始化
   - ReLU → Kaiming 初始化
   当前可能用了不当的初始化导致初始激活值就落在 Sigmoid 饱和区。

4. **降低学习率**：从 0.01 降到 0.001 或更低，配合学习率调度器（如 StepLR、CosineAnnealingLR）。

5. **添加梯度裁剪**：`torch.nn.utils.clip_grad_norm_(model.parameters(), max_norm=1.0)`，防止梯度爆炸。

6. **增加网络深度但使用残差连接**（ResNet 风格），让深层网络也能训练。

**评分标准**：每项合理建议得约 1.25 分，4 项即满分。答案不必与上述完全相同，方向正确即可。

```python
import os
from PIL import Image
from torch.utils.data import Dataset

class SkinDataset(Dataset):
    def __init__(self, root_dir, transform=None):
        self.transform = transform
        self.samples = []  # 存储 (img_path, label_idx) 对

        # 获取所有子文件夹名作为类别名
        class_names = sorted(os.listdir(root_dir))
        self.class_to_idx = {name: i for i, name in enumerate(class_names)}

        # 遍历每个类别文件夹
        for class_name in class_names:
            class_dir = os.path.join(root_dir, class_name)
            if not os.path.isdir(class_dir):
                continue
            for img_name in os.listdir(class_dir):
                img_path = os.path.join(class_dir, img_name)
                self.samples.append((img_path, self.class_to_idx[class_name]))

    def __len__(self):
        return len(self.samples)

    def __getitem__(self, idx):
        img_path, label = self.samples[idx]
        img = Image.open(img_path).convert('RGB')
        if self.transform:
            img = self.transform(img)
        return img, label
```

`transform` 中虽然做了 ToTensor()，但没有 Normalize。虽然这不会导致无法训练，但不归一化会让模型收敛更慢。更关键的是——训练集和测试集的 transform 不一致会导致 train/test 分布不匹配。

**Bug 4：CrossEntropyLoss 前 logits 未经过 Softmax——这不是 bug！**

`nn.CrossEntropyLoss()` 内置了 LogSoftmax，所以 forward 直接输出 logits 是正确的。这个不是 bug。

**补充 Bug（如果存在）：如果测试集 transform 中包含 Normalize，需要确保和训练集参数一致。**

**参考答案**：

```python
# ===== 修复 1：训练集和测试集使用不同的 Transform =====
train_transform = transforms.Compose([
    transforms.RandomHorizontalFlip(),
    transforms.RandomCrop(32, padding=4),
    transforms.ToTensor(),
    transforms.Normalize((0.4914, 0.4822, 0.4465),
                         (0.2023, 0.1994, 0.2010))
])

test_transform = transforms.Compose([
    transforms.ToTensor(),
    transforms.Normalize((0.4914, 0.4822, 0.4465),
                         (0.2023, 0.1994, 0.2010))
])

train_data = datasets.CIFAR10(root='./data', train=True,
                               transform=train_transform)
test_data = datasets.CIFAR10(root='./data', train=False,
                              transform=test_transform)

# ===== 修复 2：forward 中添加 ReLU 激活函数 =====
def forward(self, x):
    x = self.pool(torch.relu(self.bn1(self.conv1(x))))   # 加了 relu
    x = self.pool(torch.relu(self.bn2(self.conv2(x))))   # 加了 relu
    x = x.view(x.size(0), -1)
    x = torch.relu(self.bn3(self.fc1(x)))                 # 加了 relu
    x = self.fc2(x)  # 分类头不需要激活，CrossEntropyLoss 内置 Softmax
    return x
```

**致命问题——内存完全不够**：

- 单张仍约 11 MB（存的是原始尺寸 tensor）
- 1 万张 × 11 MB ≈ 110 GB

- 224×224×3×4 = 约 0.6 MB/张
- 1万张 × 0.6 MB ≈ 6 GB → 可行

**（2）方案 B 的优化（5分）**

**参考答案**：

**num_workers > 0 的潜在问题**：

- `self.img_paths` 和 `self.labels` 是 Python list，在 `__init__` 中创建。当 `num_workers > 0` 时，Windows 使用 `spawn` 方式创建子进程，每个子进程会重新导入模块并重新执行 `__init__`。如果 list 很大（50 万个路径字符串），每个 worker 进程都会在内存中有一份拷贝，导致**内存翻倍**（主进程 + N 个 worker 各一份）。
- Linux 使用 `fork`，子进程继承父进程内存空间（Copy-on-Write），这个问题相对较小。

**优化后的 DataLoader 配置**：

```python
from torch.utils.data import DataLoader
import os

train_loader = DataLoader(
    dataset,
    batch_size=64,
    shuffle=True,
    num_workers=min(4, os.cpu_count()),  # 不是越大越好
    pin_memory=True,                      # 加速 CPU→GPU 传输
    persistent_workers=True,              # 避免每个 epoch 重启 worker
    prefetch_factor=2,                    # 预取下一批数据
    drop_last=True                        # 保持 batch 大小一致（对 BN 重要）
)
```

**评分标准**：
- 指出 worker 的内存复制问题得 2 分
- DataLoader 配置合理（含至少 3 个优化参数）得 3 分

**（3）进一步加速策略（5分）**

**参考答案**（两种，每种 2.5 分）：

**策略一：使用 LMDB 或 HDF5 存储预处理数据**

- 原理：将原始 JPEG 图片预先解码并 resize 到训练尺寸，存入 LMDB（内存映射数据库）或 HDF5 文件。训练时通过内存映射（mmap）直接读取，避免了每次 JPEG 解码和 resize 的 CPU 开销。
- 代价：需要额外的磁盘空间存储预处理后的数据，且预处理是 one-time cost。

**策略二：使用 NVIDIA DALI 进行 GPU 加速的数据预处理**

- 原理：DALI（Data Loading Library）将数据解码和增强从 CPU 卸载到 GPU 上执行。JPEG 解码、resize、翻转等操作在 GPU 上并行处理，解放 CPU 去做其他事情。避免了 CPU→GPU 之间的数据搬运瓶颈。
- 适用：有 NVIDIA GPU 且数据预处理是瓶颈时。

**策略三：在 `__getitem__` 中使用 LRU 缓存**

- 原理：使用 `@functools.lru_cache` 缓存最近用过的图片（已解码的），因为多个 epoch 会重复访问同一张图片。但注意要限制缓存大小防止内存溢出。

**策略四：数据预取 + 异步 IO**

- 原理：使用额外的线程在后台预读磁盘，将下一个 batch 的数据提前加载到内存中，让 GPU 不等 I/O。

**评分标准**：每种策略 2.5 分（原理清楚得 1.5 分 + 适用场景/代价分析得 1 分）。
