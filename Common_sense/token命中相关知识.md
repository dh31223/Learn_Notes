## 1. 请求格式：不是发 .json 文件

### 1.1 发出去的是什么

- HTTP 请求 = 请求头 + 空行 + 请求体
- 请求体可以是多种格式，由 `Content-Type` 头指定：

| Content-Type | 长相 | 典型场景 |
|---|---|---|
| `application/json` | `{"a": 1}` | 现代 API 主流 |
| `application/x-www-form-urlencoded` | `a=1&b=2` | 传统网页表单 |
| `multipart/form-data` | 分段的二进制块 | 上传文件 |
| `application/protobuf` | 纯二进制，人不可读 | gRPC、高性能服务 |

### 1.2 JSON 格式 vs .json 文件

- **JSON 格式**：一种字符串编码约定，用于传输
- **.json 文件**：本地磁盘文件扩展名，通常作配置文件
- **共同点**：数据结构一样
- **区别**：生命周期不同——一个是"传输用的"，一个是"存盘用的"

### 1.3 完整传输链路

```
你的数据: {"a": 1}
  → UTF-8 字节: 7B 22 61 22 3A 20 31 7D
  → TCP 切成"段"，加端口号
  → IP 加源/目标地址，变成"数据包"
  → 网卡变成电/光/无线电信号发出
```

每层包一层，服务器收到后反向拆开，按 Content-Type 把字节流反序列化回数据结构。

## 2. 无状态 vs 有状态 API

### 2.1 核心区别

| | 无状态 | 有状态 |
|---|---|---|
| 比喻 | 每次打电话自报家门 | 对方认得你的声音 |
| 服务器 | 金鱼记忆，请求结束=清零 | 有个笔记本，session 存着 |
| 你的请求 | 每次携带全部历史 | 只发增量 |
| 扩缩容 | 随便加机器 | 麻烦，上下文绑在特定机器 |

### 2.2 为什么 LLM API 选无状态

1. **扩缩容简单**：无状态随便换机器处理，有状态的机器挂了 session 全丢
2. **容错性好**：你这台机器挂了，换一台接着处理，因为每个请求自包含全部上下文
3. **计费透明**：每次 input token 全在请求里看得见

### 2.3 HTTP vs 上层协议

- HTTP 协议本身是**无状态**的
- "有状态 API" 一般靠上层机制模拟：
  - Cookie/Session：服务器给 session_id，在 Redis/DB 里查上下文
  - WebSocket：连接不断，上下文一直活着
  - gRPC stream：双向流，服务端内存 hold 状态

## 3. Token 缓存命中机制（前缀缓存）

### 3.1 缓存的是什么

缓存的不是"对话文本"本身，而是 **Transformer 内部每层的 K/V 矩阵**。

回忆 Attention 机制：
```
算第 N 个 token 的 attention 时，需要前 N-1 个 token 的 K 和 V
→ K 和 V 只依赖前面的 token，前面没变就不用重算
```

### 3.2 匹配方式：精确前缀匹配，不是语义匹配

- 缓存看**字面是否相同**，不看话题是否相近
- 前缀 = system + 全部 messages，一个字没改就命中
- 话题从工作跳到英语再跳回工作——只要在时间线里是直线追加的，前缀就没断过

### 3.3 每轮缓存都会滚动更新

```
第 1 轮: 缓存 [system, u1, a1]
第 2 轮: 缓存 [system, u1, a1, u2, a2]  ← 新 KV 追加进去了
第 3 轮: 缓存 [system, u1, a1, u2, a2, u3, a3]
```

不是第 1 轮拍的照片焊死不动，是录像机，每轮都在接着录。

### 3.4 价格对比（以 Opus 4 为例）

| 类型 | 价格 |
|---|---|
| input（常规） | $15 / 百万 token |
| input（缓存命中） | $3.75 / 百万 token（打 2.5 折） |
| output | $75 / 百万 token |

- output 是常规 input 的 **5 倍**
- output 是缓存命中的 **20 倍**
- 新内容永远付钱，旧内容不修改就一直白嫖

### 3.5 缓存什么时候会断

| 情况 | 结果 |
|---|---|
| 正常追加对话 | 不中断，持续命中 |
| 编辑了前面某条消息 | **断崖**——前缀不一致 |
| 重新开会话 | 归零——system 重新写入 |
| 暂停超过 5 分钟（Anthropic） | 缓存过期，归零 |
| 客户端自动裁剪历史 | 前缀变化，归零 |

## 4. 上下文压缩与缓存重建

### 4.1 压缩前后对比

```
压缩前: [system] + [u1 a1 u2 a2 ... u50 a50] + [u51 当前问题]
        └────────── 全部命中 ──────────┘      └─全新─┘

压缩后: [system + 精炼摘要] + [u51 当前问题]
        └── 全新！缓存不存在 ──┘  └─全新─┘
```

### 4.2 压缩后各轮费用变化

| 轮次 | 缓存状态 | 费用 |
|---|---|---|
| 压缩后第 1 轮 | 全断，全部重算 | **贵**（一次性过路费） |
| 压缩后第 2 轮 | 新前缀建立，命中 | 便宜 |
| 压缩后第 3+ 轮 | 持续命中，前缀更短 | **比压缩前更便宜** |

### 4.3 为什么需要压缩

不压缩的代价：
- 第 50 轮 input 可能已 5 万 token，请求体巨大，延迟越来越高
- 一旦意外超时（5 分钟），5 万 token **全重算**，直接炸
- 上下文窗口有上限（如 1M），终究会爆

压缩 = 一次性付过路费重建缓存，换后续轻量、安全、不爆窗口。

### 4.4 压缩带来的副作用

多次压缩后 VS Code 插件前端会卡顿：
- DOM 节点堆积（前端没同步清理旧消息）
- 摘要层层叠加
- Node.js 内存碎片

建议：使用 `Ctrl+Shift+P → Developer: Reload Window` 或直接换新会话。

## 5. 思考链（reasoning_content）

### 5.1 与 messages 的关系

```json
{
  "choices": [{
    "message": {
      "reasoning_content": "嗯，用户问的是...",  // 思考过程
      "content": "正式回复..."                  // 正式回复
    }
  }]
}
```

| | reasoning_content | content |
|---|---|---|
| 你看到的 | 折叠在"思考中" | 正式回复 |
| 占 messages 吗 | **不占** | 占，下一轮变成历史 |
| 计费吗 | 不算 context | 算 |
| 缓存会命中吗 | 不参与 | 参与 |

### 5.2 关键理解

思考链是**旁路通道**——服务器返回给客户端展示，但不进入下一轮的 messages 数组。不会撑爆上下文窗口，也不会拖慢后续对话。

## 6. 上下文窗口（1M context）

### 6.1 1M = 1M token，不是 1M 字节

- token ≠ 字节
- 一个中文字 ≈ 1-2 token
- 1M token ≈ 几十到上百万中文字

### 6.2 超限会怎样

不是"舍弃前面的"，而是**直接报错**：

```
400 Bad Request
"Input too long"
```

API 不会帮你偷偷截断，要求客户端自己解决。

### 6.3 VS Code 插件的上下文圈圈

- 客户端用**字符数/词数估算**（没跑 tokenizer），精度 ±10~20%
- 显示 "0%" 时通常还有几万 token 余量
- 圈圈 0% = **黄牌警告**，服务器 400 = **红牌罚下**

## 7. Skill 调用流程

Skill 调用本质是多了一轮工具调用往返：

```
你的消息 → 服务器匹配关键词 → output: tool_use("Skill", "feynman-check")
         → 客户端读取本地 SKILL.md → 发回 tool_result
         → 服务器拿到 skill 指令 → 按规则输出
```

tool_use + tool_result 在 messages 数组里是**两条额外消息**，和其他工具调用（Bash、Read）本质相同。

## 8. 省钱实践总结

| 做 | 不做 |
|---|---|
| 追加，别编辑历史 | 改前面的话 |
| system 放不变的东西 | system 里塞当前时间 |
| 控制输出长度（output 比 input 贵 5-20 倍） | 让我展开 20 种方案 |
| 长文档一次喂完 | 分多次"还有这个还有那个" |
| 大转弯开新会话 | 一个会话聊 8 个领域 |
| 5 分钟内连续对话 | 聊一句去上厕所回来继续 |
| 压缩 1-2 次后主动换会话 | 反复压缩到天荒地老 |

## 9. 一张图总结全链路

```
你打字 "1+1等于几"
  → 客户端拼成 JSON: {model, system, messages: [全部历史 + 新问题], max_tokens}
  → HTTP POST 到服务器
  → 服务器跑 tokenizer，数 token
  → 查 KV Cache：前缀命中？命中 → 跳过重算
  → Transformer 只算增量 token
  → 输出 content（计费 output token）
  → 可能同时输出 reasoning_content（不计费，不占 messages）
  → 客户端渲染回复
  → 新 token 的 KV 追加进缓存
  → 下一轮重复
```
